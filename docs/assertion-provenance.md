## 分析單位

**一個 `expect(...)` 呼叫 = 一條斷言。** 一個 expect 裡包了多個主張時，
**取其中最沒有依據的那一個**來歸類（保守方向見下）。

---

## 五類

| 類 | 名稱 | 判準 | 要不要附證據 |
|---|---|---|---|
| **P0** | OA 支持 | 主張直接寫在 OA 的 `steps` / `expect` / `note` 裡，或是它的無歧義改寫 | 引 OA 的哪一句 |
| **P1** | Gherkin 支持 | OA 沒有，但 `.feature` 有 | 引 `.feature` 的哪一步 |
| **P2** | 公開契約可推 | OA 與 `.feature` 都沒有，但可由**公開、可引用的產品契約**推出（官方規格、API 文件、官方 E2E） | **必附檔名＋行號＋凍結 SHA** |
| **P3** | 測試基礎建設 | 不是需求層的行為主張：前置守衛、可見性檢查、資料備妥檢查 | 不列入分母 |
| **P4** | 無依據（over-claim） | 是可檢查的行為主張，但 P0–P2 都不支持 | — |

**只有 P4 叫 over-claim。** P1 與 P4 都是「Gherkin／測試比 OA 強」，差別在 P1 有機會被
Gate 2 的 ledger 記到，P4 發生在下游、目前沒有任何東西記錄。

P3 的例子（這些**不算**行為主張）：
```js
await expect(deleteButton).toBeVisible();          // 點之前確認它在
await expect(page1Articles.length).toBeGreaterThan(0);  // 確認資料備妥
```

## 兩個難判的形狀，規則寫死

### 1. 模糊詞的操作化

> OA：「收藏後按鈕與計數反映這次操作。」`note`：「該文章的初始收藏數為 0。」
> 斷言：`expect(count).toContainText('1')`

**判準：以 OA 陳述的前置條件為前提，該主張的真值是否被蘊含。**
初始值 0 ＋ 一次收藏 → 1 是蘊含，因此 **P0**。
若 OA 沒有固定初始值，「變成 1」就不被蘊含 → **P4**。

⚠️ 蘊含必須是**第三方查得動的**，不能是裁決者的直覺 ——
**裁決者必須引出蘊含它的那一句原文**。引不出來就不算蘊含。

### 2. 換一種 oracle

> Gherkin：`the deletion is completed`
> 斷言：`expect(res.status).toBe(404)`（直接打 API）

UI 上看不到，跟伺服器端真的刪掉了，**是兩個不同的主張**。
**判準：換觀測管道 ≠ 同一個主張。** 要算 P2 必須引得出公開 API 契約裡
「DELETE 之後該資源不存在」那一條（檔名＋行號＋SHA）。引不出來 → **P4**。

### 3. 可見性斷言：守衛還是主張

> 斷言：`await expect(deleteButton).toBeVisible();`

**同一個形狀可能是 P3 也可能是行為主張**，而這個測試床有一整族需求就是在講可見性
（「非作者看不到編輯鍵」「留言刪除鍵只有留言作者看得到」）。
把可見性一律歸 P3 會讓那一族整個從分母消失。

**判準兩條，都要成立才算 P3：**

1. **要求與 Gherkin 都沒有主張這個元素「在這個時間點」是否可見**；且
   ⚠️ **提到這個元素不等於主張它的可見性。** 要求說「收藏後按鈕反映這次操作」，
   講的是按鈕在動作**之後**的狀態，不是它在點擊**之前**看不看得到。
   （第二個判定器把「要求提到這顆按鈕」讀成「要求主張它可見」，
   因此補上時間點。**這是凍結前的最後一次修改**，之後判準不再依結果調整。）
2. 它出現在**觸發動作之前**，作用是確保接下來的操作有對象。

只要要求或 Gherkin 有一句在講這個元素看不看得到，它就是**行為主張**（P0／P1），
不是守衛 —— 即使寫法一模一樣。

⚠️ 這一條是陽性對照抓出來的：判定器把一條 Gherkin 有、要求沒有的可見性斷言
判成 P3。形狀不足以分辨，**要看要求／Gherkin 有沒有在講它**。

## 保守方向：模稜兩可一律判**有依據**

研究假設是「下游會加入沒有帳的主張」。**把模稜兩可判成 P4 會灌水我們自己的假設**，
所以規則反過來：**判不準時歸到 P0／P2**，並**另外計一個 borderline 計數**。

正式報告要同時給兩套數字：

- **strict**：borderline 全部算 P4
- **lenient**（主報告用）：borderline 全部算 P0／P2

**結論必須在兩套下都成立**，否則只能報成「取決於判準」。

## 誰來判

1. **裁決者是獨立的新對話**，只拿到：OA 原文、`.feature`、那一條斷言、以及公開契約的可引用片段。
   **拿不到**：產生這支測試的對話、其他條斷言的判定結果。
2. **輸出結構化**，一條斷言一筆：
   `{assertion, class: P0|P1|P2|P3|P4, citation, borderline: bool}`。
   `class` 是 P0／P1／P2 時 `citation` 必填，填不出來就不能給那一類
   （這條是在擋「說它有依據但指不出來」）。
3. **不可用字串比對代替判定**（本專案已因此犯錯三次，見 `HANDOFF.md`〈一定不能破的規則〉第 14 條）。
4. **人工抽查**：隨機抽 N 條由研究者覆核，報 agreement。
   LLM 裁決者不可作唯一真值（`LITERATURE.md` 硬點 4）。

## 主要指標

對每一支生成的測試：

```
行為主張總數      = P0 + P1 + P2 + P4          （P3 不計）
無帳可查的主張    = P4
Gate 2 可攔的主張 = P1
無帳比例          = P4 / (P0 + P1 + P2 + P4)
```

三組條件（baseline ／ self ／ blind）各自報這四個數字。

⚠️ **這個指標不需要測試在乾淨版通過**，因為它讀的是原始碼。
所以它不受目前端到端管線 18 支只有 3 支通過的影響。

## 這份判準自己的弱點（先寫下來）

- **P2 的邊界取決於「公開契約寫得多細」。** 契約寫得細，同一條斷言就從 P4 變 P2。
  所以 P2 的每一筆都要附引用，讓讀者自己判。
- **「無歧義改寫」沒有形式化定義。** 目前靠裁決者引原文 ＋ 人工抽查兜住，
  這是這份判準最軟的一塊。
- **一個 expect 包多個主張時取最弱的那個**，會讓斷言數偏低、P4 比例偏高。
  要不要改成拆成多條，是還沒定的取捨。
